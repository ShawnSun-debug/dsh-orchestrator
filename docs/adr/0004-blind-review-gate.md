# 0004 派发前由零上下文评审者判一次任务卡

## 状态

已决定（2026-11-05）

## 背景

主代理只做规划与验收（见 `CONTEXT.md` 的「闸门」），但它的规划本身没有任何独立检查。
计划写错时，错误会被 worker 并行执行、放大，回到主代理时已经看不出是哪一层错的。
同类系统普遍的做法是再开一个 agent「给建议」，实测会退化成仪式：模型不会拒绝批评，
被要求必须给建议时就会生产放之四海皆准的句子，主代理读两轮之后开始跳过它。

## 决定

在 `review` 段由一个**零上下文评审者**对任务卡判定一次，结论是四字段结构：

```yaml
verdict: BLOCK | IMPROVE | PASS
target: "任务卡里的哪个字段 / 原句"
fix: "改完之后那句话长什么样"
failureMode: "原计划会失败的具体机制，不是「可能有问题」"
checked: ["完成定义", "写白名单", "验收命令", "回退策略"]
```

三条硬约束：

1. **`PASS` 合法。** 要求「至少给一条改进建议」会让评审失去信号，改为要求「必须列出查了哪几项」。
2. **盲的是推理链，不是事实。** 评审者拿到任务卡与真实文件路径，拿不到主代理的心路。
3. **每卡一次预算。** `BLOCK` 打回主代理重规划并附 `failureMode`，不自动重评、不自动改写。

评审者是一次受控派发，因此**评审类派发不再触发评审**（写在闸门代码里，不写在提示词里），否则递归。
评审路由单独一条配置，默认跟随 worker 路由。

## 替代方案与不选的理由

**主代理自审一次（提示词要求）**：零成本，但自己审自己与没有审的差别只在措辞。
**强制至少一条建议**：产量有了、信号没了，见背景第二段。
**每个 worker 派一次评审**：`orchestrate` 一次可派 64 条目，评审成本线性贴着条目数涨；评审的单位必须是**一次派发调用**。
**异步补审（先发后评）**：延迟为零，但它已经不是闸门，主代理可以无视结论。

## 后果

- 每次高风险派发多一次模型调用与一个往返延迟。
- 评审者可能为空或误判；`PASS` 的 `checked` 清单是可追溯的，能事后归因。
- 任务卡从「提示词里的约定」变成「结构化输入」，主代理多一份填卡成本。
- 低风险派发不审，靠分级阈值兜住成本；阈值表本身需要随使用修订。
