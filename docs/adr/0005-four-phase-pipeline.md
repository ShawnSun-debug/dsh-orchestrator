# 0005 派发主干切成 plan → review → dispatch → settle 四段

## 状态

已决定（2026-11-05）

## 背景

现有实现里 `delegate`、`orchestrate`、`retry`、`supervise` 是四条并列链路：
派发的入口、失败的处理、外部观测各自一套，不知道「一次派发现在处在哪」。
新增评审还得再挂一条，会让并列链路变成五条。

## 决定

四段串行，每段一个模块，一次派发在任一时刻只处在一段：

```text
plan     读消息、产出任务卡（主代理自己完成，闸门保证不许跳）
review   零上下文评审者判卡（ADR 0004），BLOCK 回到 plan
dispatch 派发 workers：内部复用现有 delegate/orchestrate/retry/supervise
settle   标记 settled、日志留档、摘出活跃集与巡检到期集
```

`dispatch` 段内部仍是现有的异步派发 + 巡检 + 重试，不重写；重画的是**它前后的契约**。
`settle` 是新增的收口动作，当前实现里没有。

## 替代方案与不选的理由

**两层：复用会话阶段投影 + 派发生命周期**：改动最小，但状态分散在两处，
「这张卡现在在哪」要跨两套结构拼，正是现在四条链路各自为政的原因。
**事件驱动，一切状态由事件投影**：可观测性最好，接近 superagent 那套 sqlite 的形态；
但那不是一次重画能付得起的成本，且现有 `supervise.js`/`retry.js` 已经按日志做过一轮事件化。

## 后果

- 长跑任务仍然卡在 `dispatch` 段里等，四段并没有让等待变短。
- `settle` 只摘除活跃与巡检，不删数据；活跃集会随时间膨胀，需要另定压缩策略。
- 四段是否成立，取决于每段的边界能不能用纯数据表达；一旦某段需要回头改前一段的产出，四段就该降级为三段。
